第一章

智能体推理与执行概述

在动手搭建智能体之前，先建立两张地图：一张"思维地图"——智能体如何推理（推理范式）；一张"组织地图"——多个推理单元如何协同（编排架构）。本手册十章，讲清这两张图。

1.1 为什么智能体需要推理范式与编排架构

大语言模型本质是一个"下一个词预测器"：直接把复杂任务抛给它，它既不会主动分解问题，也不知道何时该查资料、何时该验证自己的答案。推理范式就是给模型的一套"怎么思考"的工作方法——先想后做、边想边做、做了再改；编排架构则是把一个个"思考单元"组织成可靠系统的骨架——谁先谁后、何时分支、何时汇合。

没有范式，答案质量完全靠运气，模型"想到哪算哪"；没有编排，单次推理无法覆盖需要多步骤、多工具、多角色协作的真实任务。二者合起来，才构成智能体应用的地基。

一个类比：推理范式 = 单个员工的工作方法论（CoT、ReAct……）；编排方式 = 团队的流程制度（顺序、并行、循环……）；运行底座 = 办公场地与工具箱（LangGraph、Spring AI……）。方法论再好，没有制度和场地，也做不成项目。

1.2 核心概念边界：推理范式、编排方式、运行底座

三个概念在日常讨论中经常被混用，先划清边界：

概念回答的问题关注层次典型代表

第二章

ReAct 推理-行动框架Reasoning + Acting

让模型把"推理"与"行动"交织进行——想一步、做一步、看结果、再想下一步。今天几乎所有智能体框架的 Agent Loop，都是 ReAct 的变体。本项目可演示

2.1 范式核心解释

ReAct 的核心是一个三元素循环：Thought（思考）→ Action（行动）→ Observation（观察）：

  • Thought：模型显式写出当前一步的推理——"我已知道什么、还缺什么、下一步该做什么"；
  • Action：据此调用一个工具（搜索引擎、计算器、数据库查询、代码执行……）；
  • Observation：把工具返回的结果追加进上下文，作为下一轮思考的输入。

循环往复，直到模型判断信息已足够，输出最终答案（Final Answer）。

关键洞察在于把推理轨迹显式写进上下文：模型能依据环境反馈及时纠正方向。与"只推理不行动"（纯思维类，容易幻觉）和"只行动不推理"（盲目连环调工具）相比，ReAct 显著降低了幻觉率与无效调用，是工具型智能体的默认选择。

2.2 标准执行流程

用户问题

Action选择并调用工具
Observation获取工具返回结果，写入上下文
信息足够？
是

否 · 继续循环 ↺

2.3 适用场景与局限性

✓ 适用场景
  • 需要外部实时信息的问题：天气、新闻、股价、汇率
  • 需要精确计算或多工具组合的任务
  • 答案依赖环境反馈的开放型问题
✗ 局限性
  • 纯推理问题用不上工具，白付循环成本
  • 每轮携带全部历史，长任务 token 消耗大
  • 工具选错会连环放大，缺乏自愈机制（见第九章）

2.4 典型示例问题

  • Q1
    今天北京的气温是多少？适合户外跑步吗？ Thought：需要实时天气 → Action：调用天气查询 → Observation：28℃、空气良 → Thought：对照跑步适宜条件 → 输出"适合，注意补水"。
  • Q2
    搜索"量子计算"的定义，并解释它和传统计算的区别。 Action：搜索工具取回定义 → Observation 后提炼"叠加态、并行计算"要点 → 组织对比解释输出。
  • Q3
    查找最近的科技新闻，并总结三条最重要的动态。 Action：新闻搜索工具 → Observation 返回多条 → Thought：逐条评估重要性 → 汇总三条摘要。

第三章

纯思维推理范式Pure-Thinking Paradigms

纯思维类范式不调用外部工具，全部推理在模型内部完成。它们不改变模型的能力，而是改变"思考的组织形式"--链、树、分解--以此撬动复杂问题的解答质量。本章讲三种基础形态，另外三种增强形态（投票、验证、组网）见第六章。

3.1　CoT 思维链Chain of Thought本项目可演示

"把思考过程写出来，答案自然更准。"

CoT 让模型显式生成中间推理步骤、再给结论：一步到位靠"直觉"，在复杂问题上容易翻车；分步推理把大问题拆成模型能稳定把握的小步，每一步都很简单，串联起来就能解难题。CoT 是所有推理范式的起点--ToT 改变链的形状（变树），Self-Ask 改变链的构造方式（自问分解），其余范式都以它为底座。

问题输入
分解识别需要哪些中间步骤
逐步推理每一步显式写出推理过程
最终答案

图 3-1　CoT 标准执行流程

✓ 适用场景
  • 数学计算与证明、逻辑推理
  • 多步计算、需要中间过程的问题
  • 需要展示推理过程的教学讲解
✗ 局限性
  • 线形单路径，一步错则步步错
  • 无法获取外部信息，知识盲区直接幻觉
  • 需要探索多个方案时力不从心（→ ToT）
  • Q1
    鸡兔同笼：35 个头、94 只脚，鸡兔各几只？ 假设全是鸡得 70 只脚 -> 差 24 只脚 -> 每换一兔多 2 脚 -> 兔 12、鸡 23，逐步列式呈现。
  • Q2
    如果今天是周三，100 天后是星期几？ 100 ÷ 7 = 14 余 2 -> 周三顺推 2 天 -> 周五。
  • Q3
    三段论：所有人都会死，苏格拉底是人，所以？ 大前提（所有人会死）+ 小前提（苏格拉底是人）-> 逐步推出"苏格拉底会死"。

3.2　ToT 思维树Tree of Thoughts本项目可演示

"多思考几条路，选最好的走。"

ToT 在每个推理节点生成 k 个候选分支，用模型（或外部评估器）为分支打分：保留高分分支继续展开、剪掉低分分支，最终从存活路径中回溯选出最优解。它把 CoT 的"单链"扩展成"一棵会修剪的树"，本质是在推理过程中做带剪枝的搜索（DFS / BFS）--思考不再是走到哪算哪，而是"探索-评估-取舍"。

问题输入
生成 k 个候选分支每步探索多条思路
评估打分
高分 · 保留 ↺ 逐层展开
继续深入生成下一层分支
低分 · 剪枝
放弃该路径不再消耗算力
回溯选最优路径
最终答案

图 3-2　ToT 标准执行流程：分支展开-评估剪枝-回溯取优

✓ 适用场景
  • 有明确评价标准的探索题：算 24 点、数独、8 皇后
  • 多方案权衡决策：出行计划、投资选择
  • 需要保留多个备选方案的规划问题
✗ 局限性
  • token 成本成倍增长（每步 k 个候选）
  • 分支打分依赖可评估标准，纯主观问题难用
  • 实现复杂度比 CoT 高一个量级
  • Q1
    用 1、3、4、6 通过加减乘除算出 24？请探索多种解法。 枚举运算组合为分支 -> 评估每支可解性 -> 剪掉死路 -> 锁定 6 ÷ (1 − 3 ÷ 4) = 24。
  • Q2
    周末出游，考虑天气、交通、预算、兴趣四个因素，选最优方案。 每个维度生成候选方案 -> 四维打分 -> 剪掉低分组合 -> 输出综合最优的出行安排。
  • Q3
    10 万元闲钱，分析股票、基金、定期存款三种方案的优劣。 三分支分别推演收益与风险 -> 逐支评估 -> 给出兼顾风险偏好的组合建议。

3.3　Self-Ask 自问自答Self-Ask本项目可演示

"把大问题拆成一串小问题，逐个击破。"

模型先对原问题自问："要回答它，我得先知道什么？"由此生成分解出的子问题队列；然后逐个回答（纯思维版靠模型内部知识，增强版可在每问处插入工具调用），每个子答案回填上下文、支撑下一问；最后综合全部子答案得出结论。它把"一步到位的多跳推理"变成显式的问答链，特别擅长 multi-hop（多跳）问题。

复杂问题
自问：需要先回答哪些子问题？
逐个回答子问题子问题 1 → 子问题 2 → …… 答案逐个回填
综合得出最终答案

图 3-3　Self-Ask 标准执行流程

✓ 适用场景
  • 多跳事实问题："蒙娜丽莎的画家还画过什么？"
  • 需要组合多个知识片段的查询
  • 子问题链式依赖的推理任务
✗ 局限性
  • 分解方向错了，全链皆错（上限取决于拆解质量）
  • 子问题串行，错误会沿链传导
  • 需要实时信息的场景不如 ReAct
  • Q1
    蒙娜丽莎的画家还画过什么著名作品？ 子问 1：作者是达芬奇 -> 子问 2：达芬奇的名作有哪些 -> 综合列出《最后的晚餐》等。
  • Q2
    深圳和广州哪个城市人口更多？GDP 各是多少？ 子问 1：深圳人口与 GDP -> 子问 2：广州人口与 GDP -> 逐项比较得结论。
  • Q3
    长江流经哪些省份？最终注入哪个海？ 子问 1：流经省份列表 -> 子问 2：入海口位置 -> 汇总回答。

第四章

规划执行类范式Plan-and-Execute

关键词是"先想清楚，再动手"：先把任务展开成一份结构化计划，再逐步执行，执行偏差还能触发重规划。与 ReAct"走一步看一步"相对，Plan-and-Execute 更像"先画路线图再出发"。本项目可演示

4.1 范式核心解释

Plan-and-Execute 由三个角色分工协作：

  • Planner（规划器）：把任务分解为有序的步骤列表，每步目标明确、可独立执行；
  • Executor（执行器）：按序执行每一步（可调用工具），并汇报结果；
  • Replanner（重规划）：执行中发现计划走不通（某步失败、信息变化）时，调整剩余步骤。

它适合步骤多、周期长的任务：计划显式化让长任务不"漂移"，过程可检查、可暂停恢复。对比 ReAct 每轮都从头思考整体方向，P&E 一次规划、按图执行--更稳定，但应变较慢。

4.2 标准执行流程

任务输入
Planner生成分步计划（结构化步骤列表）
Executor按序执行每步 · 可调用工具 · 汇报结果
计划完成且达标？
是
汇总最终结果
否 · 触发重规划 ↺
Replanner调整剩余步骤后继续执行

图 4-1　Plan-and-Execute 标准执行流程

4.3 适用场景与局限性

✓ 适用场景
  • 多步骤任务：旅行计划、行业分析报告
  • 长程任务需要稳定执行（计划显式化，可检查、可恢复）
  • 环境会变化、计划需动态调整的场景
✗ 局限性
  • 规划质量是天花板：计划错了，执行再好也白费
  • 简单任务"先规划"反而增加延迟与成本
  • 重规划逻辑实现复杂
与 ReAct 的取舍：ReAct 每轮重新思考整体（灵活，但长任务易漂移）；P&E 一次规划多次执行（稳定，但应变慢）。生产中常组合使用--用 P&E 定骨架，每个步骤内部嵌 ReAct 执行。

4.4 典型示例问题

  • Q1
    帮我制定一个为期 3 天的北京旅游计划。 Planner：拆出景点选择 / 路线编排 / 餐饮 / 预算四步 -> Executor 逐步确认信息 -> 汇总成行程表。
  • Q2
    分析电动汽车行业的投资前景，从市场规模、政策支持、竞争格局三方面入手。 计划三步走 -> 每步检索数据并分析 -> 某步数据缺失时重规划补充 -> 汇总结论。
  • Q3
    规划健康减脂方案：每周运动 3 次，控制饮食，持续 2 个月。 规划运动 / 饮食 / 复盘三模块 -> 逐周执行 -> 按体重变化数据触发重规划。

第五章

反馈迭代类范式Reflexion

引入"评估"环节：答案不是一次生成，而是"生成-评估-反思-改进"多轮打磨。Reflexion 相当于给智能体装上一本"错题本"。本项目可演示

5.1 范式核心解释

Reflexion 由三个角色循环协作：

  • Generator（生成器）：产出当前版本的答案；
  • Evaluator（评估器）：按标准打分并给出具体反馈（规则校验，或 LLM-as-judge）；
  • Reflector（反思器）：把反馈提炼成"反思记忆"--哪里错、为什么错、下次怎么改--注入下一轮生成的上下文。

循环直到评估通过或耗尽最大轮次。核心思想：用语言化的自我反馈代替参数更新，让模型"在同一个会话里越做越好"。

5.2 标准执行流程

任务输入
Generator生成当前版本答案
Evaluator评估打分 + 具体反馈
通过
输出最终答案
未通过
Reflector生成反思记忆：错在哪、怎么改
带着反思进入下一轮 ↺
回到 Generator改进版答案

图 5-1　Reflexion 标准执行流程：生成-评估-反思闭环

5.3 适用场景与局限性

✓ 适用场景
  • 有明确质量标准的生成任务：代码跑测试、文案评分
  • 需要多轮打磨的推理与证明
  • 对"一次到位"要求高的交付物
✗ 局限性
  • 多轮循环，token 成本数倍增长
  • 评估器不准会把迭代带偏（裁判很关键）
  • 一次性事实查询毫无必要

5.4 典型示例问题

  • Q1
    用 Python 写一个二分查找算法，然后优化时间和空间复杂度。 生成初版 -> 评估边界条件（off-by-one）-> 反思修复 -> 迭代至测试通过。
  • Q2
    为一款智能手表撰写产品宣传文案，要求不断迭代优化。 生成初稿 -> 按"卖点清晰 / 节奏 / 记忆点"评分反馈 -> 反思改写 -> 多轮润色。
  • Q3
    证明"任意两个奇数的平方差能被 8 整除"，请多轮审视推理过程。 生成证明 -> 逐步检查推导 -> 发现未覆盖的情形 -> 反思补全后定稿。

第六章

其他补充推理范式Self-Consistency · CoV · GoT

三大类之外，还有三种重要的"增强件"范式：它们通常不单独使用，而是套在其他范式外面进一步提升可靠性--Self-Consistency 靠"多次采样投票"，CoV 靠"生成后再验证"，GoT 靠"思维自由组网"。

6.1　Self-Consistency 自一致性Self-Consistency

"问 N 遍，少数服从多数。"

对同一问题用较高温度采样 N 条推理路径（每条都是一条 CoT），提取各自的最终答案后投票取多数派。用"众数"对冲单次推理的随机误差。实现极简（CoT + 采样 + 投票），是性价比最高的可靠性增强手段。

问题输入
采样 1
推理路径 1 -> 答案 A
采样 2
推理路径 2 -> 答案 A
采样 N
推理路径 N -> 答案 B
多数投票
胜出答案（A）

6.2　CoV 验证链Chain of Verification

第七章

智能体任务流编排方式Orchestration Patterns

推理范式解决"单个智能体怎么想"，编排解决"多个步骤 / 智能体怎么组织"。顺序、判断、循环、并行、状态机是五种控制流原语--再复杂的智能体工作流，也是它们的嵌套组合。

顺序编排

核心逻辑：步骤按固定次序逐一执行，上游输出作为下游输入，像工厂流水线。最简单也最常用，是一切编排的默认形态。

适配范式：CoTPlan-and-Execute流水线组合架构

适用场景：步骤间强依赖且顺序稳定的任务--翻译->润色->排版；提取->分析->成文。

适配范式：元智能体调度的底层机制意图识别分流

适用场景：输入差异大、处理路径不同的任务--工单分级路由；简单问题走 CoT、复杂问题走 ReAct。

第八章

范式与编排的组合落地架构Composition Architectures

真实系统从不只用一种范式。两条主流组合路径：流水线式（预先设计好阶段链，范式在固定位置就位）与元智能体式（一个"调度者"根据任务动态选范式、派子智能体）。

8.1 流水线式静态组合

核心逻辑：把端到端任务切分为固定阶段，每个阶段选定最适配的范式与模型，阶段间以结构化产物（JSON / 文档）交接。设计期确定全部控制流，运行期只走既定路线。

适用边界：任务结构稳定、可枚举（研报、工单类流程化产出），追求可预测、可审计、成本可控。不适用于路径高度动态的探索型任务。

第九章

离生产级 Harness 还缺什么The Gap to Production

前八章的范式与编排足以搭出"能跑的 Demo"。但从 Demo 到生产，缺的不是更聪明的推理，而是工程化的 Harness--包裹在模型外面的运行时管控层。本章盘点七项关键缺失。

9.1 前置认知：Harness 的核心定位与分层价值

Harness（运行时护栏与管控层）是包裹在智能体外面的运行时系统：调度执行、注入上下文、调用工具、管控边界、记录一切。类比：模型是"大脑"，Harness 是"神经系统 + 免疫系统"--大脑再聪明，没有神经系统和免疫系统也活不成。

应用层业务逻辑与用户交互
Harness 层安全护栏 · 容错自愈 · 上下文工程 · 可观测 · 成本管控
编排层工作流、状态管理与多智能体协作
范式层ReAct · ToT · Reflexion 等推理方法
模型层LLM 推理能力

图 9-1　智能体系统分层：Harness 是 Demo 与生产的分水岭

范式与编排决定"能做多聪明的任务"，Harness 决定"能不能稳定地一直做"。Demo 通常只建上三层；生产五层缺一不可。

9.2 七项关键缺失

缺失一：执行全链路安全护栏与边界管控

工具调用白名单、参数校验、危险操作人工确认（human-in-the-loop）、输出内容过滤。Demo 常把权限整个交给模型；生产必须"最小权限 + 关键动作拦截"。

缺失二：运行时容错与异常自愈

超时重试、工具降级、循环熔断（最大轮次上限）、失败回滚与检查点恢复。Demo 一错就崩；生产要"错了能自己爬起来"。

缺失三：全生命周期上下文工程

上下文窗口是稀缺资源：历史压缩、记忆分层（短期 / 长期）、检索增强（RAG）注入、无关信息裁剪。Demo 全量塞入直到溢出；生产要精打细算每一个 token。

缺失四：全链路可观测性与可调试性

每一步的输入输出、工具调用、token 消耗、延迟全量埋点（tracing），支持回放调试与评测基线。Demo 靠 print；生产靠 trace。

缺失五：资源与成本精细化管控

预算限额、模型分级路由（简单任务用小模型）、缓存复用、并发控制。Demo 不计成本；生产按千次调用核算毛利。

缺失六：多智能体协作与通信基础设施

角色定义、消息协议、共享状态（黑板模式）、冲突消解、死锁防护。Demo 两个 agent 对话即可；生产需要一条可靠的协作总线。

缺失七：环境适配与标准化接入层

工具沙箱（文件、浏览器、代码执行）、MCP 等标准协议接入、开发 / 测试 / 生产环境隔离。Demo 工具硬编码；生产走标准化接入。

9.3 智能体从 Demo 到生产的完整分层架构对照

工程级

10.4 课程核心知识点复盘

  • 三层分野：范式回答"怎么想"，编排回答"怎么组织"，Harness 回答"怎么管住"。
  • 两个最小：CoT 是最小可用推理，ReAct 是最小可用智能体。
  • 三大类范式：纯思维类（链、树、分解、投票、验证、组网）、规划执行类（边想边做、先想后做）、反馈迭代类（越改越好）。
  • 五种编排原语：顺序、判断、循环、并行、状态机--可任意嵌套组合。
  • 两条组合路线：流水线（稳、可控）与元智能体（活、上限高），生产常混用。
